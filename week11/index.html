3.6.1 Troubleshooting Methodology (OSI Bottom-Up)
  • Layer 1 (Physical): Check cables, LEDs, and interface status.
  • Layer 2 (Data Link): Check VLAN membership, MAC table, duplex/speed mismatch.
  • Layer 3 (Network): Verify IP addressing, subnet mask, default gateway, and routing table.
  • Layer 4–7: Check firewall rules, application ports, service availability.
  • Always gather symptoms first, isolate the layer, test fixes, and document.
3.6.2 ping & traceroute
  • ping <ip> — sends ICMP Echo Requests; ! = success, . = timeout, U = unreachable.
  • Start with ping 127.0.0.1 (loopback) → default gateway → remote host.
  • traceroute <ip> (IOS) / tracert <ip> (Windows) — shows each hop with RTT.
  • * in traceroute = no ICMP reply within timeout (may be filtered, not necessarily down).
  • ! in IOS traceroute = success response from that hop.
3.6.3 ipconfig, netstat & nslookup
  • ipconfig /all (Windows) — shows IP, mask, gateway, DNS, MAC, and DHCP status.
  • ip address show (Linux) or ifconfig — equivalent on Linux/Unix.
  • netstat -an — all active TCP/UDP connections with ports.
  • netstat -r — routing table on the host (equivalent to route print).
  • nslookup <hostname> — queries DNS; reveals which server is answering and the resolved IP.
  • ipconfig /flushdns — clears local DNS cache (Windows).
3.6.4 Common Issues & Solutions
  • Wrong subnet mask — hosts can't reach each other even on same switch → fix mask.
  • Missing default gateway — host can ping local subnet but not remote → add gateway.
  • Duplex mismatch — slow speeds, high errors → set both ends to auto or same speed/duplex.
  • Missing static/dynamic route — router drops packets → add route or verify protocol config.
  • DNS failure — can ping IP but not hostname → check name-server config and connectivity.

Key Concepts
ℹ️
Bottom-Up Approach: Always start at Physical (Layer 1). It's pointless to check IP settings if the cable is unplugged or an interface is shut down.
✅
Extended Ping on IOS: Type ping and press Enter (without an IP) to enter extended ping mode — set source interface, repeat count, and packet size for more precise testing.
⚠️
Firewall blocks ICMP: A ping failure does NOT always mean the host is down. Firewalls often block ICMP. Use telnet <ip> <port> or application tests to verify further.
🔧
Cisco Show Commands Priority: Start with show ip interface brief (all interfaces at a glance), then show ip route (routing table), then show running-config (full config review).

Cisco IOS Show Commands for Troubleshooting
Essential verification commands
! ── Check all interface statuses in one shot
Router# show ip interface brief
! Interface   IP-Address    OK? Method Status                Protocol
! Gi0/0       192.168.1.1   YES NVRAM  up                    up
! Se0/0/0     10.0.0.1      YES NVRAM  up                    up

! ── Inspect the routing table
Router# show ip route
! C = Connected, S = Static, R = RIP, O = OSPF

! ── View full running configuration
Router# show running-config

! ── Inspect a specific interface in detail
Router# show interface GigabitEthernet0/0
! Check for input/output errors, duplex, speed

! ── Ping and traceroute from router
Router# ping 192.168.2.1
Router# traceroute 192.168.2.1

! ── Extended ping (source address control)
Router# ping
! Target IP address: 192.168.2.100
! Repeat count [5]: 10
! Source address or interface: 192.168.1.1

🖥️ Lab 7 — Systematic Network Troubleshooting

Open the Lab 7 Packet Tracer file (pre-broken topology). Complete the following steps:

  1. Examine the topology: 2 routers, 2 switches, 4 PCs — several deliberate misconfigurations present.
  2. From PC1, run ipconfig in the command prompt and document the IP, mask, and gateway.
  3. Ping the default gateway — if it fails, check the IP settings and correct any addressing errors.
  4. On Router1, run show ip interface brief — identify any interfaces that are administratively down and bring them up.
  5. Run show ip route on Router1 — check that routes to both LANs exist; add missing static routes if needed.
  6. From PC1, ping PC3 (across routers) — if it fails, run tracert to identify where the path breaks.
  7. Use nslookup from PC1 to test DNS resolution (server provided in topology).
  8. Document each fault found, the evidence (tool/command used), and the fix applied.
